Generated by `/scenario-gap-audit`. Compares all `Component = mobile-app` scenario files in `scenarios/` (cross-referenced with `features/`) against the current implementation in `lib/screens/` (via `docs/screens/**/*.md`). Read-only analysis — no screens or client code were changed to produce this report.

## Summary

| Status | Count |
|---|---|
| Total mobile-app scenarios considered | 126 |

| ⚠️ Partial | 52 |
| ❌ Missing | 64 |

**Context that shapes almost every row:** per CLAUDE.md, no backend, no state-management library, and no CCTV protocol (RTSP/ONVIF/etc.) has been chosen yet. Every screen in the app runs on in-memory/mock data (`HomesController`, `AlertsController`, `EventsController`, `ProfileController`) that resets on restart, and live view/playback/recording all stand in with a single bundled dummy video asset. This means even scenario rows marked ✅ or ⚠️ here are UI-complete at best — none have a real device/backend behind them yet. That caveat is not repeated per-row below; see `docs/screens/**/*.md` stub notes for specifics.

## Summary of coverage by area

The app currently has strong coverage for **per-camera image/video/audio tuning** (imaging, WDR, mirror/flip, audio volume + a real Record Audio toggle, snapshot/manual-clip capture, playback event navigation) — this is where most of the 9 ✅ rows and the video/audio ⚠️ rows sit. **Recording & Storage gained the most ground overall**: a StorageScreen (SD enable/disable, capacity/free-space, a real computed time-remaining estimate, card health + non-endurance + storage-failure banners, retention presets with a feasibility warning, Format SD Card, and a deletion-history log) moved six scenarios off ❌ (FEAT-033, FEAT-049, FEAT-051, FEAT-224, FEAT-038, FEAT-037, FEAT-190 — all ⚠️ now), and let RecordingScreen's footage estimate become a real computed value instead of stub text, pushing FEAT-031 to ✅. **Camera health moved from a flat online/offline boolean to a real 3-state model** (`Camera.liveStatus`, driven by the same storage conditions): Dashboard tiles, `CameraLiveScreen`'s badge, and a new Health section on `CameraInfoScreen` now surface a "Needs Attention" state instead of misleadingly plain "Online" (FEAT-089 ⚠️, only missing sort-to-top for degraded cameras) — though this is a *different* middle state than FEAT-084 wants (that scenario specifically wants a cloud/MQTT-reachability distinction, which still doesn't exist, so FEAT-084 stays ⚠️ with updated notes). Two other areas also moved in earlier passes: **audio recording** got an independent toggle plus a persistent live-view indicator (FEAT-022 ⚠️, only missing deployment-type-aware defaults), and **access control** gained per-camera scope *assignment* (`CameraAccessScope` on `UsersInvitesScreen`, FEAT-148 ⚠️) — though still nothing *enforces* it, since there's no per-user login/session anywhere in the app (FEAT-147 stays ❌ for that reason). Everything involving a **rules engine** (schedules, class filters, templates, test mode, dwell/parking/gate rules), **offline resilience/sync** (buffering, queueing, dedup, sync-state display), **event-driven health alerts** (tamper, image-quality, lens-haze, night-vision, predictive failure, corrective guidance — these need an Alerts/AlertDetail upgrade, not just the status-badge model that now exists), **evidence integrity** (clip locking, watermarking, integrity manifests — as opposed to the storage/retention settings that now exist), OTA/firmware update messaging (no update-checking UI anywhere yet, including on `CameraInfoScreen`'s read-only firmware row), the remaining **access-control gaps** (approval workflows, audit log, installer/support roles, actual scope enforcement), and **installer commissioning workflows** (checklists, reference-view capture, site templates, test mode) is entirely unbuilt — these make up the bulk of the 66 ❌ rows. This tracks with CLAUDE.md's framing: no backend, no CCTV protocol, and no state-management layer have been chosen yet, so the app so far is a UI shell for direct per-camera settings rather than the rules/health/access/sync systems the product spec describes.
