# MultiviewScreen

- **Dart file:** `lib/screens/multiview/multiview_screen.dart`
- **Route:** none — a modal takeover pushed on the root `Navigator` (`rootNavigator: true`) from DASH-022 on [dashboard_screen.md](../dashboard/dashboard_screen.md), the same pattern `camera_live_screen.md`'s fullscreen and AI Mode use, not a nested go_router route. A nested route would still render inside the Dashboard branch's own Navigator, underneath MainShell's bottom nav bar (SHELL-001) — this screen needs to escape that entirely for an immersive, chrome-free surface, so it's a plain `MaterialPageRoute` push instead.
- **Purpose:** Watch every camera in one home at once, cycling between `1×1` (single, full screen), `2×2`, and `3×3` layouts. Distinct from the Dashboard's own grid/list layout toggle (DASH-004), which is for browsing/navigating to a single camera — this screen is a dedicated simultaneous-viewing surface. Forces landscape orientation on entry (same pattern as camera_live_screen.md's fullscreen), reverting to the app's normal portrait lock on exit. The `2×2`/`3×3` grids are built from nested `Column`/`Row`/`Expanded` (not a scrolling `GridView`) so every tile fits edge-to-edge on screen with no scrolling; a home with fewer cameras than grid cells pads the remainder with blank tiles rather than leaving gaps. Every video surface (`RTCVideoView`, WAN `VideoPlayer`, and the offline `CameraThumbnailImage` fallback) uses `BoxFit.contain`, not `.cover` — the full frame is always visible, never cropped. Each tile owns its own `LiveViewController` (LAN WebRTC / WAN HLS, same as camera_live_screen.md's single-camera session) for as long as the tile is mounted. **Dev/test only**: each tile's `LiveViewController` also reads the Dashboard's DASH-023 Force LAN/WAN override (`DebugTransportOverride`) at construction — a tile built while a non-`null` override is active connects under that forced transport, same as camera_live_screen.md's session (though unlike that screen, a tile doesn't live-reconnect if the override changes while already mounted — it picks it up fresh next time it's rebuilt, e.g. a layout change).

## Elements

| Design ID | Element | Type | Notes |
|-----------|---------|------|-------|
| MULTIVIEW-001 | Back button (overlay, top-left) | Circular IconButton over a translucent black backing | in `1×1` mode, returns to whichever grid layout (`2×2`/`3×3`) was active before the double-tap that zoomed in, without leaving the screen; in a grid layout, pops this modal takeover, returning to Dashboard with the shell's bottom nav bar and portrait lock restored |
| MULTIVIEW-002 | Home name label (overlay, next to MULTIVIEW-001) | Text over a translucent black pill | shows the home's name |
| MULTIVIEW-003 | Layout cycle button (overlay, top-right) | Circular IconButton over a translucent black backing | cycles `1×1` → `2×2` → `3×3` → `1×1` on each tap; icon reflects the active layout |
| MULTIVIEW-004 | Camera tile (repeated per camera, key suffixed `-<cameraId>`) | Grid/single-view tile | shows that camera's live video (`BoxFit.contain`) and camera name label (bottom, with a text shadow for legibility). Double-tap zooms to `1×1` (MULTIVIEW-001 restores the prior layout); tap alone does nothing (no navigation to the single-camera live-view route from a tile — reserved for the double-tap gesture instead). Requests a resolution tier sized to the tile's actual screen space — `Profile_1` (highest) in `1×1`, `Profile_2` in `2×2`, `Profile_3` (lowest) in `3×3` — via `LiveViewController`'s `initialProfile`, rather than every tile opening at full resolution regardless of how small it's displayed; switching layout reconnects each tile at the new tier |
| MULTIVIEW-006 | Empty state | Text | shown when the selected home has no cameras |
| MULTIVIEW-007 | Loading indicator (per tile) | CircularProgressIndicator | shown while that tile's `LiveViewController` is connecting/reconnecting |
| MULTIVIEW-008 | Retry button (per tile) | IconButton | shown when that tile's connection attempt failed; retries `LiveViewController.connect()` |
| MULTIVIEW-009 | Reorder cameras button (overlay, top-right, left of MULTIVIEW-003) | Circular IconButton over a translucent black backing | pushes [multiview_reorder_screen.md](multiview_reorder_screen.md), a dedicated full-page screen for reordering this home's cameras |
| MULTIVIEW-010 | Spotlight shortcut (overlay, left edge, `1×1` mode only) | IconButton / CircularProgressIndicator while busy | only shown when `camera.spotlightCapable != false`; toggles the camera's spotlight via `DeterrenceClient`/`WanDeterrenceClient`, same instant-apply pattern as camera_live_screen.md's LIVE-018 |
| MULTIVIEW-011 | Siren shortcut (overlay, left edge, `1×1` mode only, below MULTIVIEW-010) | IconButton / CircularProgressIndicator while busy | only shown when `camera.sirenCapable != false`; same pattern as MULTIVIEW-010, action `"siren"` (camera_live_screen.md's LIVE-045) |
| MULTIVIEW-012 | Warning shortcut (overlay, left edge, `1×1` mode only, below MULTIVIEW-011) | IconButton / CircularProgressIndicator while busy | only shown when `camera.warningCapable != false`; same pattern as MULTIVIEW-010, action `"warning"` (camera_live_screen.md's LIVE-046) |

MULTIVIEW-013 (previously a `showModalBottomSheet` reorder UI) is retired — reordering moved to the dedicated [multiview_reorder_screen.md](multiview_reorder_screen.md), opened via MULTIVIEW-009.

Cameras that are offline (`Camera.isOnline == false`) or have no saved connection show the same offline thumbnail + "camera off" treatment as camera_live_screen.md's offline state, without a MULTIVIEW-007/008 id of their own (no connection is ever attempted for them).
