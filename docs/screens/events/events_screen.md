# EventsScreen

- **Dart file:** `lib/screens/events/events_screen.dart`
- **Route:** `/events`
- **Purpose:** Recorded events/playback history — a browsable timeline of recorded video clips (motion/person/vehicle/etc.), distinct from AlertsScreen's push-style notification feed. A multi-level zoomable timeline (Day down to 1-minute granularity, VMS-app style) shows clip distribution for a chosen day, with duration-proportional event blocks; a right-side filter panel (mirroring AlertsScreen's) narrows by camera/type. Tapping a clip (in the timeline or the list) plays it back fullscreen. Mock/local data only (see `EventsController`); no backend/CCTV protocol integration yet.

### Timeline ruler

Went through six design iterations, adapted from user-provided visual references rather than ported literally:

1. An HTML/CSS reference with a fixed-width 24-hour track and a draggable playhead — translated to `GestureDetector`/`LayoutBuilder`/`Stack`/`Positioned`, plus `InteractiveViewer` for pinch-to-zoom. Rejected — the user wanted horizontal scrolling, not pinch-zoom.
2. A screenshot reference of a scrollable ruler with a fixed center playhead (the ruler scrolls under the playhead, rather than the playhead moving over a fixed ruler). Implemented via `SingleChildScrollView` + a `ScrollController` listener. Missing: visible hour tick lines (not just labels), and the user asked for "zoom" too at this point.
3. Re-added zoom via `InteractiveViewer` in `constrained: false` pan+zoom mode, deriving time from the inverted `TransformationController` matrix instead of a linear scroll offset. Added short vertical tick lines above each hour label.
4. The user clarified "pinch to zoom" was a miscommunication; they wanted the ruler simply bigger by default, not a zoom gesture. Reverted to plain `SingleChildScrollView`/`ScrollController`, but enlarged: `pixelsPerHour` 100→140, track height 60→90, thicker tick lines/playhead, larger hour labels.
5. The user then provided a detailed spec (modeled explicitly on Hikvision/Dahua/Milestone/Nx Witness mobile VMS apps) asking for pinch-to-zoom again, but through **discrete named levels** (Day → Hour → 30 min → 15 min → 5 min → 1 min) that progressively reveal finer tick/label detail — not a continuous visual scale of the same content. Implemented via `InteractiveViewer` for live elastic pinch feedback, snapping `_levelIndex` on `onInteractionEnd` based on the gesture's final scale, then resetting to a crisp 1x transform re-centered on the pre-gesture time. Event ticks became duration-proportional blocks (EVT-008) instead of fixed-width ticks, satisfying the "recording segments expand with zoom" part of the spec — this made the earlier `_minTickGap`/`_tickPositions()` decluttering pass (added for a prior request about overlapping simultaneous events) unnecessary, since real proportional widths naturally separate at higher zoom; it was removed.
6. **Current design** — the user asked for explicit +/- buttons instead of the pinch gesture. `InteractiveViewer`/`TransformationController` were removed entirely (no longer needed — nothing else required a scale-capable widget) and replaced with the simpler `SingleChildScrollView`/`ScrollController` approach from step 2, since panning no longer needs to coexist with a competing pinch recognizer. EVT-022 (zoom out) and EVT-023 (zoom in) call `_zoomOut`/`_zoomIn`, which step `_levelIndex` and re-center via `ScrollController.jumpTo` (the scroll-offset equivalent of the old matrix-based `_centerOn`). The discrete zoom-level system itself (6 named levels, duration-proportional blocks) from step 5 is unchanged — only the trigger mechanism (buttons vs. pinch) and the underlying pan widget changed. The spec's "optional" 10-second/5-second maximum-zoom level remains intentionally skipped (marked optional in the user's own spec); the deepest implemented level is 1-minute ticks.

The reference's 3-color legend (Motion/Person/Alert) was extended to 4 (adding "Other") throughout, to cover `EventType` values that don't fit those three buckets (vehicle/animal/package).

7. **Extracted into a shared widget.** The user wanted the Camera Live screen's Playback tab to use the same timeline design. `_TimelineScrubber`/`_TimelineScrubberState` were generalized into `CameraTimeline` (`lib/widgets/camera_timeline.dart`) — a controlled widget taking generic `TimelineMarker`/`TimelineRange`/`TimelineLegendEntry` data plus per-element `Key`s, so each screen keeps its own design-ID prefix. This also added a recording-availability solid blue band (EVT-025/LIVE-036) with gray dead zones for gaps, and (Playback-only) draggable clip-range handles (LIVE-023/LIVE-024) and hard drag-into-gap snapping (`enforceRecordingBounds`), neither of which apply to this screen.

### Navigation

Tapping an event (EVT-008 or EVT-013) no longer plays the clip directly from this screen — it navigates to `EventDetailScreen` (`docs/screens/event_detail_screen.md`) via `context.push('${EventsScreen.routeName}/${EventDetailScreen.routeName}', extra: event)`, same pattern as `AlertsScreen` → `AlertDetailScreen`. Playback (and download/share/delete) now live entirely on that screen. The `_playEvent`/`_FullscreenEventPlayer` code that used to live here was removed.

### Data model

`RecordedEvent` (`lib/models/event.dart`) is intentionally separate from `Alert` — `EventType` is a narrower enum than `AlertType`, containing only trigger types that produce a playable clip (motion/person/vehicle/animal/package/faceRecognized/strangerDetected/loitering/lineCrossing/intrusion). System/status alert types (offline, low battery, tampered, etc.) don't have a recording and stay exclusive to `AlertType`. `EventTypeDisplay` (`lib/models/event_type_display.dart`) adds `timelineColor`/`timelineBucketLabel` getters alongside the existing `label`/`icon`, condensing the 10 types into the 4 timeline color buckets.
