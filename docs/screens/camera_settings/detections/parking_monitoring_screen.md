# ParkingMonitoringScreen

- **Dart file:** `lib/screens/camera_settings/parking_monitoring_screen.dart`
- **Route:** `/dashboard/live/:cameraId/settings/detections/parking-monitoring`
- **Purpose:** Reached from the "Parking Monitoring" row on [detections_screen.md](detections_screen.md). Distinct from [vehicle_detection_screen.md](vehicle_detection_screen.md) — that screen is a plain "did a vehicle appear" toggle, this one owns zone-based occupancy tracking and its own violation rules. Lets the user draw up to 20 zones on the preview, each one of three types: **Parking Slot** (a real, countable bay — occupied/free, "wrong bay" if a vehicle overlaps a neighboring slot), **Open Area** (an unmarked lot/section with no painted lines — counts vehicles inside the boundary against a user-entered estimated capacity, does not judge position), or **Restricted / No-Parking** (never counts as a space; a vehicle inside fires a violation after a dwell-time threshold). State is staged locally and only applied when Save is tapped — **entirely local-only for now**: no `camera_api` capability exists yet for per-zone vehicle occupancy classification (confirmed via `ui-api-gap-audit`, only a plain `VehicleDetected` boolean exists), so every zone's status badge and the summary card show "No live data yet" rather than a fabricated count — this repo removed all dummy/fake media/data (2026-09-08/09) and this screen must not reintroduce fake numbers. Wiring real occupancy requires a new capability from the senior engineer first.

| PARK-001 | Screen title (AppBar) | Text | "Parking Monitoring" |
| PARK-002 | Save button (AppBar action) | `SettingsSaveButton` (shared widget, `lib/widgets/settings_save_button.dart`) | disabled until a field changes or while saving; tapping triggers the full-screen `SavingOverlay` while simulating a camera round-trip (`simulateCameraSave`, local-only — no backend capability exists yet), then shows a "Changes saved" snackbar, or an error snackbar with the button re-enabled on failure |

Each zone's outline color always reflects its type — blue for Parking Slot, teal for Open Area, red for Restricted — not live occupancy (there is none yet). Fixed 2026-09-09 in two passes: (1) a zone's type color used to be replaced entirely by the generic selection color the instant it was drawn (every new zone is auto-selected), so a just-drawn Restricted zone showed blue instead of red until something else was selected — selection now shows as a thicker outline/brighter fill and a white vertex-handle ring instead of a hue swap; (2) the in-progress draft (before "Finish zone" is tapped, PARK-007/008's flow) was still missed by pass (1) — it never received a type color at all, so mid-draw it always showed the plain selection color regardless of which type was picked at PARK-006, making a Restricted zone look identical to a Slot zone while still being drawn. | PARK-006 | New-zone type selector | Row of 3 `ModeTile`s ("Parking Slot" / "Open Area" / "Restricted"), same tile widget as [privacy_mode_screen.md](../video_display/privacy_mode_screen.md)'s PRIV-002 | selects which type the *next* drawn zone becomes; does not affect already-drawn zones |

| PARK-013 | Wrong-bay dwell time slider | Slider, shown only when ≥1 Parking Slot zone exists | separate, shorter-default threshold from PARK-012 — a car briefly straddling a neighboring slot's line while parking isn't a violation; still straddling after this long is. | PARK-016 | Occupancy summary card | Read-only `GlassCard`, above the zone list | "Slots: — / N configured", "Open areas: capacity M configured", "Restricted: K zones" — deliberately shows configured counts only, not fake occupied/free numbers, with a one-line note ("Live occupancy needs camera support — not available yet") until a real capability exists to replace the placeholder with actual "X occupied · Y free" |
| PARK-018 | Draw-new-zone surface | `PolygonDrawSurface` (shared widget, `lib/widgets/drawable_zone.dart`), overlaid on PARK-003 underneath the existing `PolygonOverlay`s | alternative to PARK-007: drag a finger around the outline directly on the preview to trace a custom zone in one continuous gesture, instead of PARK-007's default pentagon. The raw drag is lightly throttled during capture, then run through Ramer–Douglas–Peucker simplification once the gesture ends, keeping only the points that actually define a corner. Fixed 2026-09-09: a single fixed simplification pass left the result's vertex count entirely at the mercy of hand-steadiness — normal small wobble on a phone screen could produce 9-10 vertices for what was meant as a simple shape, visibly messier than PARK-007's always-clean 5-point default. The tolerance now grows (up to 8 attempts) until the result is at or under 5 vertices — matching PARK-007's fixed 5-point default exactly, so both creation methods converge on the same vertex count; a trace that genuinely needs more corners keeps them if widening can't get under the cap without dropping below a valid polygon's minimum 3 points. **Real bug, fixed 2026-09-09**: a trace close enough to a straight line has no real corners, so simplification correctly collapses it to just its 2 endpoints — below the 3 a polygon needs. The fallback for that case used to be every single raw, unsimplified touch sample instead, so a mostly-straight drag rendered as a dense trail of dozens of tiny dots along the line rather than a usable shape. A straight line isn't a valid enclosed zone at all, so that case is now discarded outright (no zone created), the same as a too-short drag already was. A trace that closes into 3+ points after simplification becomes a real zone the instant the gesture ends, immediately selected and vertex-draggable like any other zone. **Real bug, fixed 2026-09-09**: `PolygonOverlay`'s decorative `CustomPaint` layer was sized to the *entire preview*, not just its own polygon's bounding box, and — being un-ignored — Flutter treats a `CustomPaint`'s hit-test region as its whole declared size regardless of what was actually painted there. The instant the *first* zone finished drawing, its invisible full-preview hit box silently swallowed every future touch anywhere on the preview, including a brand-new PARK-018 trace attempted nowhere near it — reproducible with two zones in *completely separate* corners of the preview, ruling out any actual spatial/vertex-handle collision. Fixed by wrapping that paint layer in `IgnorePointer` (only the vertex handles need to be interactive) — verified via an automated widget test that traces a Slot zone then a Restricted zone in sequence. This also affects [person_detection_screen.md](person_detection_screen.md)'s exclusion zones (same `PolygonOverlay`), though it was never observable there since that screen has no drag-trace-on-preview surface to be blocked. |

| PARK-019 | Discard button (in PARK-017) | TextButton | discards the change and leaves |
| PARK-020 | Save button (in PARK-017) | FilledButton | saves via `_save()` before leaving |

Zones are capped at 20 (`maxParkingZones`, deliberately higher than the shared 8-zone `maxDrawableZones` used elsewhere — a real lot easily has more than 8 bays). Each zone stores its type (`ParkingZoneType.slot | openArea | restricted`), an optional label, and (Open Area only) an estimated capacity — a new model, not a reuse of `DrawableZone`/`PolygonZone`, since neither carries a type/capacity field.

**Retired design ID**: `PARK-008` ("Finish zone" button) — removed 2026-09-09 along with the point-by-point draft flow it belonged to (see PARK-007).

On successful save, values persist through `HomesController.updateCamera` — reopening this screen reflects whatever was last saved. Real occupancy/violation detection, and therefore PARK-003's live-status coloring and PARK-016's real numbers, require a new `camera_api` capability that doesn't exist yet (see this screen's Purpose note) — flagged for the senior engineer, not something `/integrate-client-code` can close today.
