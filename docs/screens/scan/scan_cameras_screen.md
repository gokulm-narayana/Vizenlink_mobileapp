# Scan for cameras

Two-part flow: a centered scanning popup, then a dedicated results page.

## Scanning popup

- **Dart file:** `lib/screens/scan/scanning_popup.dart`
- **Two variants, two callers:**
  - `showScanningPopup` — a small centered dialog box (not full-width), dimmed background behind it, shown for a fixed 2s timer. Used only by `ScannedDevicesScreen`'s own Rescan button (`SCAN-006`), where it's purely visual feedback alongside the real rescan already running in the background (the results list itself has no inline loading indicator during a rescan).
  - `showDashboardScanningPopup` — shown directly over the Dashboard from its "Add camera" button (`DASH-019`), running the real LAN scan (`scanForCameras()`, `lib/app_state/camera_scan.dart`) itself rather than a fixed timer, and cancelable via the back gesture/button only (no inline Cancel button). Replaces the old behavior where Dashboard navigated straight to `ScannedDevicesScreen` and let that screen's own SCAN-011 loading state cover the scan — this popup runs the *same* `scanForCameras()` call once, and hands its result to `ScannedDevicesScreen` via `state.extra` (see that screen's row below), so the scan never runs twice back-to-back. If the scan finds zero cameras, the popup switches to a "No cameras found" state (SCAN-018) instead of closing into an empty results screen.

| Design ID | Element | Type | Notes |
|-----------|---------|------|-------|
| SCAN-001 | Scanning popup | Centered glass card (not a Material `AlertDialog`) | spinner + "Scanning for cameras…" text, shown while a scan is in flight. Shared shape used by both `showScanningPopup` (fixed 2s) and `showDashboardScanningPopup` (real scan) |
| SCAN-014 | "Stop scanning?" confirmation | AlertDialog | `showDashboardScanningPopup` only, and only while still scanning (not shown once SCAN-018's "no cameras found" state is reached) — shown when the back gesture/button is used while the SCAN-001 popup is showing (`PopScope`, `canPop: false` during scanning). The popup does not dismiss on its own |
| SCAN-015 | "Stop scanning" button | FilledButton, inside SCAN-014 | confirms stopping — closes the SCAN-001 popup and returns `null` to the caller (Dashboard stays on its own screen, no navigation to `ScannedDevicesScreen`). Does **not** cancel the underlying `scanForCameras()` call itself — `camera_api` has no cancellation support for the in-flight WS-Discovery/probe calls, so they're left to finish in the background and their result is simply discarded |
| SCAN-016 | "Keep scanning" button | TextButton, inside SCAN-014 | declines — closes SCAN-014 only, SCAN-001 keeps waiting on the scan as before |
| SCAN-018 | "No cameras found" message | Icon + Text, inside the popup | `showDashboardScanningPopup` only — replaces the spinner/SCAN-001 content in place (same dialog, doesn't navigate) once the scan completes with zero results. Also shown on a scan error, same as an empty result |

`SCAN-002` (Cancel button, inline in the SCAN-001 popup) is retired — do not reuse this ID.

## ScannedDevicesScreen

- **Dart file:** `lib/screens/scan/scanned_devices_screen.dart`
- **Route:** `/dashboard/scan`
- **Purpose:** Run a real LAN discovery scan (`scanForCameras()`, `lib/app_state/camera_scan.dart` — `camera_api`'s `WsDiscoveryClient` plus per-candidate NuraEye/ONVIF probing), filter to genuine VizenLink/NuraEye devices, probe each remaining candidate's real identity/setup-state, and let the user set up and add found cameras to the currently selected home. Discovery, filtering, and per-candidate probing are all real; "Connect" verifies the entered credentials against the real camera before adding it (see Notes).

## Notes

- Reached only from the Dashboard's "Add camera" AppBar button (`DASH-019`): tap → SCAN-001 popup (`showDashboardScanningPopup`, cancelable via SCAN-002/SCAN-014) runs the real scan over the Dashboard → on completion (not cancellation), push to `/dashboard/scan` with the results already attached via `state.extra`, so this screen's SCAN-011 initial-load scan is skipped.
- Discovery lives in the shared `scanForCameras()` (`lib/app_state/camera_scan.dart`), not inline in this screen — `WsDiscoveryClient.scanMulticast()` runs first; if it finds nothing, `scanUnicast()` (subnet sweep) runs as a fallback, matching the client's own documented tiering. Called from three places, always the same function: the Dashboard's SCAN-001 popup, this screen's own SCAN-011 initial load (only when not given `initialResults`), and every SCAN-006 rescan (behind `showScanningPopup`'s fixed-timer SCAN-001).
- **Multicast reliability (Android).** `scanForCameras()` holds an Android `WifiManager.MulticastLock` (via the `flutter_multicast_lock` plugin, a no-op on iOS/other platforms) for the `scanMulticast()` call only, released immediately after — without it, the Wi-Fi radio's power-saving filter can silently drop incoming multicast packets on some devices, which is part of why the `scanUnicast()` fallback exists at all. Requires `android.permission.CHANGE_WIFI_MULTICAST_STATE` (declared in `AndroidManifest.xml`) and, on iOS, `NSLocalNetworkUsageDescription` (declared in `Info.plist`) — iOS 14+ silently blocks *all* local-network traffic, including this multicast scan itself, without that key present at all (no permission prompt, no fallback, nothing).
- **VizenLink/NuraEye-only filtering.** WS-Discovery's ONVIF probe matches *any* `NetworkVideoTransmitter` on the LAN, not just this product's cameras. Every candidate is first challenged with `NuraeyeClient.areYouNuraeyeDevice()` (unauthenticated — a fixed challenge/response digest, no credentials needed, 3s timeout) and dropped from the results entirely (never shown, not even as an unrecognized row) if it doesn't answer correctly — so a neighbor's unrelated ONVIF camera or NVR responding to the same discovery probe never appears in this list.
- **Identity/setup-state detection.** WS-Discovery only yields a device's network address (host/port) — no identity or setup state. Every candidate that passes the VizenLink filter above is then probed concurrently (`Future.wait`, not sequentially) with `OnvifDeviceClient.getDeviceInformation()` using the factory-default credentials (`admin`/`password`, 3s timeout). A candidate that rejects them already has custom credentials ("Configured") and keeps the `"Camera at <host>"` placeholder name, since the app has no way to ask an already-configured camera for anything else without knowing its real credentials. One that accepts them is factory-reset ("Unconfigured") and gets a further `getDeviceIdentity()` call (ONVIF `GetScopes`) for its row's name: the camera's own configured display name if it has set one, otherwise its `model` as a placeholder (manufacturer is deliberately omitted from that fallback — every device here is already known to be a VizenLink/NuraEye camera, so it'd be redundant).
- **The setup dialog's own Connect flow repeats this same `getDeviceIdentity()` lookup** (alongside its existing `getSerialNumber`/`getNetworkInterfaceInfo` best-effort calls) once real credentials are confirmed — this is what actually names a camera that required manually-entered credentials (the "Configured" path never got a name from the scan-time probe above, since that probe's default credentials were rejected). Whichever name comes back here wins over the scan-list placeholder when the camera is added.
- **"Connect" (SCAN-010) now verifies credentials for real.** On tap it calls `OnvifDeviceClient.getDeviceInformation()` with the entered username/password against the camera's actual LAN IP; a rejection or timeout shows an inline error (reusing the existing error `Text`) and keeps the dialog open rather than adding a broken camera. On success it best-effort also calls `getSerialNumber()` (→ `Camera.thingName`, needed later for WAN) and `getNetworkInterfaceInfo()` (→ `Camera.macAddress`) — neither failing blocks setup, per `CameraConnection.thingName`/`macAddress`'s own "best-effort, never blocks onboarding" convention. `Camera.manufacturer`/`model`/`firmwareVersion`/`serialNumber`/`hardwareId` are populated from the verified `DeviceInformation` instead of staying at placeholder `'—'` values.
- The entered host/username/password are persisted onto the new `Camera` (see `Camera.connection`), which is what [camera_info_screen.md](../camera_settings/camera_info_screen.md)'s "Sync from camera" button (and the auto-sync below) uses to make LAN calls.
- **Auto-sync on add.** Right after `HomesController.addCamera` succeeds, the shared `syncCameraFromDevice` helper (`lib/app_state/camera_sync.dart`) fires automatically for the new camera — fire-and-forget, not awaited, so it doesn't delay returning to the Dashboard. It fetches timezone and a real snapshot in addition to the device/network/capability fields the Connect-time check already verified, filling in fields that check alone doesn't cover.
- **Widget tests for this screen (`test/widget_test.dart`) cannot currently complete in a sandboxed/CI environment without real LAN access** — `WsDiscoveryClient`'s UDP multicast/unicast scan never returns candidates, so the screen never leaves its SCAN-011 loading state. This is a pre-existing environment limitation (confirmed unchanged before/after the SCAN-010 verification work above), not something introduced by it.
- Default stub credentials: username `admin`, password `password`.
- Styling: SCAN-007 and SCAN-010 use the app's glass/gradient visual language (`GlassCard`, rounded input fields, gradient-filled primary button) rather than default `AlertDialog` styling, matching Login/Signup.
- Superseded the earlier modal-bottom-sheet version of this flow.
