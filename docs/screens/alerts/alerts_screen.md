# AlertsScreen

- **Dart file:** `lib/screens/alerts/alerts_screen.dart`
- **Route:** `/alerts`
- **Purpose:** Notifications list — motion/person/vehicle detections, camera offline/online, and other alerts across all cameras. Filterable by read state (All/Unread/Read), home, camera, type, and date; supports swipe-to-mark-read, swipe-to-delete-with-undo, and can arrive pre-filtered to a specific camera (from AlertDetailScreen's related-alerts row). Mock/local data only (see `AlertsController`); no backend/push integration yet.

### Filter panel

Replaces the earlier chip-row design (itself a replacement for the original modal bottom-sheet). A single Filter icon (ALERT-003) in the app bar opens ALERT-015, a `Drawer` assigned to `Scaffold.endDrawer` — Flutter renders `endDrawer` sliding in from the screen's right edge natively, opened programmatically via a `GlobalKey<ScaffoldState>` rather than `Scaffold.of(context)` (the State's own `context` sits *above* the `Scaffold` it builds, so `Scaffold.of` can't find it from there).

The panel is intentionally an **apply-on-confirm** flow, not instant-apply: `_FilterPanel` is a separate `StatefulWidget` seeded from the screen's current filters (`initialHome`/`initialCameras`/`initialType`/`initialDate`) but keeps its own staged copies internally, only calling `widget.onApply(...)` when ALERT-021 is tapped. The panel is given a `ValueKey` derived from the *currently applied* filter values (not the staged ones) — this forces a fresh `_FilterPanelState` (re-seeded from the latest applied values) the next time the drawer is reopened after an Apply, while leaving the State untouched (so in-progress staged edits survive) across unrelated rebuilds, e.g. toggling the All/Unread/Read segment while the drawer happens to be open.

Home and Type use `RadioListTile` under a `RadioGroup` ancestor (the pre-3.32 `groupValue`/`onChanged` params on `RadioListTile` itself are deprecated). Camera stays a plain `CheckboxListTile` list since it's multi-select.

Earlier design note (still relevant to why filter-panel layout gets tested on-device, not just widget-tested): `DropdownButton`/`OutlinedButton` inside `AppBar.bottom` or a horizontal `ListView` previously triggered real infinite-width layout crashes on-device in this screen's older designs (a plain `MaterialApp`-hosted widget test did not reproduce this) — always verify filter-panel layout changes on a real device or simulator, not just `flutter test`.

### Navigation

- Tapping a notification list item (ALERT-006) marks it read and pushes `AlertDetailScreen` via `context.push('/alerts/detail', extra: alert)`.
- `AlertsScreen` optionally accepts `initialCameraFilter`, `initialTypeFilter`, and `initialUnreadOnly`, sourced from a single `(String, AlertType, bool)` Dart record passed as `state.extra` on the `/alerts` route in `main.dart` (`extra is (String, AlertType, bool) ? extra : null`, then `.$1`/`.$2`/`.$3`). Used when AlertDetailScreen's "Unread notifications — {camera}" row navigates back with `context.go('/alerts', extra: (cameraName, AlertType.motion, true))` — camera filter, type filter, and the Unread segment of the read-state toggle all apply together. Because `AlertsScreen` lives inside a `StatefulShellBranch` (bottom-nav tab), its `State` persists across repeat visits, so a `didUpdateWidget` override re-applies newly-arrived `initialCameraFilter`/`initialTypeFilter`/`initialUnreadOnly` values each time (plain `late` field initializers only run once and silently stop working on the second visit). This wiring went through three iterations: first only the camera name was passed (Type silently never applied), then camera+type were added (the read-state toggle still silently stayed on "All"), then `initialUnreadOnly` was added to fix that too — `_ReadFilter` itself stays private to this file, so the public param is a plain `bool`, translated internally.
