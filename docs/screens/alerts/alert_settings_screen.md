# AlertSettingsScreen

- **Dart file:** `lib/screens/alerts/alert_settings_screen.dart`
- **Route:** `/alerts/settings`
- **Purpose:** Per-camera alert configuration, three real `camera_api`-backed sections per camera, all built from that camera's own reported capabilities (never a hardcoded list): **Alert Types** (does an event type generate an alert at all), **Response Actions** (which action(s) auto-fire when a detection event triggers), and **Deterrence** (live status + shared auto-stop duration for manual/automatic triggers). Reached from [alerts_screen.md](alerts_screen.md)'s ALERT-022 button.

## Elements

| Design ID | Element | Type | Notes |
|-----------|---------|------|-------|
| ALERTSET-001 | App bar title ("Alert Settings") | Text | |
| ALERTSET-003 | Camera list | `ListView.separated` | One section per camera across every home in `HomesController.value.homes` (not just the currently-selected home) |
| ALERTSET-004 | Camera name | Text, per section, keyed `ALERTSET-004-{cameraId}` | Shows the home name as a subtitle underneath when the user has more than one home; omitted when there's only one |
| ALERTSET-005 | Master "Alerts" switch | `Switch`, per section, keyed `ALERTSET-005-{cameraId}` | Reflects whether *any* currently-loaded event type is enabled (`true` if at least one value is `true`) — deliberately "any", not "every": an all-enabled reading would flip this off the moment a single detection type is turned off while others stay on, and tapping it to "fix" that would then re-enable every type, including ones deliberately left off. Toggling it is still a bulk action — sends a single `setEventPreferences` call with every one of this camera's `supportedEventTypes` set to the new value, not just a partial change — it's only the *displayed* on/off state that reads "any" rather than "all". Disabled (greyed, no `onChanged`) until the section has been expanded at least once (so the type list is known) |
| ALERTSET-006 | Expand/collapse row | `InkWell` wrapping the name + chevron, keyed `ALERTSET-006-{cameraId}` | Tapping expands/collapses this section's content; on first expand, fires `CapabilitiesClient.getCapabilities()`, `EventPreferencesClient.getEventPreferences()`, and — only when the camera's capabilities call for them — `EventResponseActionsClient.getEventResponseActions()` and `DeterrenceClient.getDeterrenceStatus`/`getDeterrenceDurations`/`getDeterrenceDurationOptions` (all via `Future.wait`, one round trip batch, not fetched for every camera on screen open — only on demand). Disabled when the camera has no saved connection (ALERTSET-008 shown instead) |
| ALERTSET-007 | Detection-type switch | `SwitchListTile`, one per entry in that camera's `supportedEventTypes`, keyed `ALERTSET-007-{cameraId}-{eventType}` | Label is the wire event-type string reformatted from PascalCase to spaced words (e.g. `"PersonDetected"` → "Person Detected"). Instant-apply: each flip sends its own single-key `setEventPreferences({type: value})` immediately, with its own inline spinner (`secondary` slot) while in flight — no draft/Apply step, matching the Live page's shortcut-tile pattern rather than the full settings-screen Apply convention |
| ALERTSET-008 | "No connection" label | Text, keyed `ALERTSET-008-{cameraId}` | Shown in place of ALERTSET-005 for a camera with no saved `CameraConnection`; that camera's row can't expand either |
| ALERTSET-009 | Loading indicator | `CircularProgressIndicator`, per section | Shown in place of the section's content while the first load is in flight |
| ALERTSET-010 | Load-failed retry | Text + `TextButton`, per section | Shown in place of the section's content if the capabilities or preferences fetch fails (the required calls); Retry re-runs the whole batch. Response Actions/Deterrence sections instead just render empty if only their own optional fetch failed — see Notes |
| ALERTSET-011 | Response Actions section header | Text, per camera, keyed `ALERTSET-011-{cameraId}` | Shown only when `supportedEventDeterrenceOptions` is non-empty (i.e. this camera has at least one detection event type eligible for an automatic response) |
| ALERTSET-012 | Response-action type row | Column (label + ALERTSET-013 chips), one per key in `supportedEventDeterrenceOptions`, keyed `ALERTSET-012-{cameraId}-{eventType}` | Label reformatted the same way as ALERTSET-007. Only detection event types appear here — state-change types (`VideoModeChanged`/`PrivacyModeChanged`) never have deterrence options and so never get a row |
| ALERTSET-013 | Response-action chip | `FilterChip`, one per action `supportedEventDeterrenceOptions[type]` lists as eligible (a subset of `siren`/`spotlight`/`warning`/`mobile_alert`), wrapped in a `Wrap` for responsive line-wrapping on narrow screens, keyed `ALERTSET-013-{cameraId}-{eventType}-{action}` | Selected state reflects `EventResponseActionsClient.getEventResponseActions()[type]`. Instant-apply: toggling sends `setEventResponseActions({type: newFullActionList})` — a full-replace of that type's action array, not additive — with an inline spinner replacing the chip's label while in flight. `mobile_alert` has no physical camera effect (read locally by this app to decide whether to show a push notification) but is toggled identically to `siren`/`spotlight`/`warning` |
| ALERTSET-014 | Deterrence section header | Text, per camera, keyed `ALERTSET-014-{cameraId}` | Shown only when the camera reports at least one of `sirenCapable`/`spotlightCapable`/`warningCapable` |
| ALERTSET-015 | Deterrence action row | Column (status dot + label + value + ALERTSET-016 slider), one per capable action, keyed `ALERTSET-015-{cameraId}-{action}` | Status dot reflects `DeterrenceStatus.isActive(action)` (green = currently active, grey = inactive) — read-only here; manual triggering itself stays on the Live page's Spotlight/Siren/Warning tiles, not duplicated here. Value label shows the pending duration, unit is "s" (seconds) for siren/spotlight or "plays" for warning (a repeat count, not seconds — `warning_repeat_count`) |
| ALERTSET-016 | Duration slider | `Slider`, per action, keyed `ALERTSET-016-{cameraId}-{action}` | Bounds come from `DeterrenceClient.getDeterrenceDurationOptions()` (`siren_seconds_min/max`, `spotlight_seconds_min/max`, `warning_repeat_count_min/max`) — never hardcoded, per `.claude/rules/mobile-app-screen-conventions.md`'s "camera-reported bounds only" rule (this API's own doc comment cites a specific prior incident: an earlier hardcoded 0–60s range let a value of `0` degenerate to "never really activates"). Dragging only updates the local pending value/label live; the actual `setDeterrenceDurations({key: value})` call fires on `onChangeEnd`, not per drag frame. Reverts to the last camera-confirmed value if the commit fails |
| ALERTSET-017 | Reload button | `ReloadSettingsButton` (shared widget, `lib/widgets/reload_settings_button.dart`), right-aligned above ALERTSET-007, one per expanded section, keyed `ALERTSET-017-{cameraId}` | Re-runs this camera's full load batch (capabilities + preferences + response actions + deterrence). Per-camera rather than a single screen-wide Reload — matches this screen's deliberate on-demand-per-camera-section fetch design (see Notes), not a single global reload that would hit every camera on the list at once. Disabled while that camera's section is already loading |

## Notes

- Every write (`setEventPreferences`, `setEventResponseActions`, `setDeterrenceDurations`) goes through the LAN call (`NuraeyeClient`) first, with a WAN retry (`WanEventPreferencesClient`/`WanEventResponseActionsClient`/`WanDeterrenceClient`, only if the LAN call fails and `connection.thingName` is known) per `.claude/rules/mobile-app-screen-conventions.md`'s LAN/WAN convention. None of the three "list what this camera supports" reads (`supportedEventTypes`, `supportedEventDeterrenceOptions`, capability flags) have a WAN equivalent — only `CapabilitiesClient` (LAN-only) can discover them — so a camera with no LAN connection at all shows ALERTSET-008 and the whole section can't be expanded, even though writes could otherwise go over WAN once the lists were known some other way.
- `EventPreferencesClient`'s and `EventResponseActionsClient`'s own doc comments in `packages/camera_api` (plus `API_REFERENCE.md`/`SETTINGS_API_GUIDE.md`) both name an anticipated `EventSettingsScreen` (and, in the docs, a `mobile_app/lib/features/alerts/event_settings_screen.dart` path that doesn't exist in this repo) as the intended consumer — this screen is that consumer, now covering all three capabilities: Alert Types, Response Actions, and Deterrence duration/status.
- If the required calls succeed (capabilities + `getEventPreferences`) but an *optional* one fails (`getEventResponseActions`, or the three `Deterrence*` calls), that specific section is simply omitted rather than blocking the whole camera section with ALERTSET-010 — a camera with, say, no deterrence hardware but working alert-type toggles still shows a fully usable section.
- Not wired to `AlertsController`/`CameraAlertsHub` at all — every write here edits what the *camera itself* generates/does (device-side, applies to every delivery path including third-party ONVIF/NVR clients, not just this app), independent of the separate client-side "snooze" toggle on `alert_detail_screen.md`'s ALERTDET-017, which only affects this app's own display of already-delivered alerts.
