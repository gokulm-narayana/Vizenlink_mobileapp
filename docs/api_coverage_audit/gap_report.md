`API_REFERENCE.md`'s own "Generated REST clients" section states the entire `Rest*Client` family
(including this one) is "currently unused by `NuraeyeClient`... exists as a ready-made typed
surface for future use," auto-generated from an OpenAPI spec, never hand-edited. Its actual
capabilities (WiFi SSID/signal/set, timezone list) are already covered by the hand-written

(`iotBrokerEndpoint`/`kvsStreamName`) — internal WAN deployment plumbing, not user-facing
settings content. Building a duplicate REST-based path for already-covered functionality isn't a
real gap, so this is deliberately left unbuilt rather than counted as 🆕.

## Notes on scope

- `packages/camera_api` itself is the network layer; screens are audited against whether they call
  the app-side client-code wrappers/classes it exposes (per `docs/client_code/camera_api.md`), not
  against the raw package directly.
- `alerts_api_config.md` documents model/config classes only (no behavior of its own) — it isn't
  counted as separately "coverable" by any screen; its consumer (`camera_alerts_hub.md`) is what
  screens actually call.
- Where a screen's core settings are wired but one sub-element (e.g. a fallback list, an app
  version string) is a small hardcoded piece, that sub-element is broken out as its own ❌ row
  rather than dragging the whole screen's status down.
- Part B (API → UI) deliberately does not exhaustively enumerate every ONVIF imaging parameter or
  every generated REST client method — classes already wired into a mapped screen (per Part A)
  were checked at the class level, not the individual-field level, and pure transport/plumbing
  (`CameraConnection`, `IotCommandClient`, `WanAuth`, `KvsPlaybackClient`, `WsDiscoveryClient`)
  was excluded as never having its own UI by design.
